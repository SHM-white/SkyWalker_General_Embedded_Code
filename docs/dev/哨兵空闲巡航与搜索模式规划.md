# 哨兵空闲巡航与搜索模式规划

> 状态：设计记录，暂不实现功能代码。待当前云台、遥控、安全链路、视觉通信等基本功能测试完成后，再按本文分阶段接入。

## 1. 当前结论

RM 哨兵常见的“空闲摆头 / 巡航搜索”本质上是**行为决策 + 云台目标生成**，不应下沉到 PID、电机驱动或 SafetyManager 中。

结合 SkyWalker 当前结构，建议职责划分为：

- `CommandManager` / 后续 autonomous producer：决定当前是手动、跟踪目标还是进入搜索。
- 云台搜索规划器：在搜索状态下生成 yaw / pitch 的目标角度或角速度。
- `CommandRouter`：只负责把已经形成的 `RobotCommand` 路由到本地主控或另一块主控，不承担搜索策略。
- `GimbalAxis`：只执行目标，不理解“巡航/自瞄”等高层语义。
- `GlobalSafetyManager` / `GimbalLocalSafety`：始终保留最高优先级的失能、Hold、超时与限位保护。
- Motor / PID：继续只负责闭环跟踪。

核心原则：**决定“为什么转”放上层，决定“转到哪里/多快”放搜索规划层，决定“怎么稳定转到目标”留给 GimbalAxis/PID。**

## 2. 当前代码基础

当前 `sentry_gimbal` 已经形成如下主链路：

```text
RemoteState
    ↓
ManualCommandMapper
    ↓
OperatorIntent
    ↓
GlobalSafetyManager
    ↓
CommandManager
    ↓
RobotCommand
    ↓
CommandRouter
    ↓
LocalGimbalCommand
    ↓
gimbalTask
    ↓
GimbalAxis
    ↓
Motor / PID
```

现有 `GimbalCommand` 已支持：

- `Disabled`
- `Hold`
- `Rate`
- `AbsoluteAngle`

因此第一版巡航不需要为了“能转起来”就修改电机层或重新设计云台控制协议。

目前 `CommandManager` 只真正处理手动模式，代码中已明确注明 autonomous command 需要未来独立 producer。这个位置正适合作为后续自动行为接入点。

## 3. 建议状态与优先级

概念上建议至少区分：

```text
DISABLED
MANUAL
AUTO_AIM_TRACK
AUTO_AIM_SEARCH
```

优先级建议：

```text
安全失能 / 故障
    > 手动接管
    > 视觉有效目标跟踪
    > 空闲搜索巡航
    > Hold
```

其中搜索状态只在“允许自动模式 + 安全链路正常 + 当前没有可跟踪目标”时成立。

视觉重新获得稳定目标后，应退出 `AUTO_AIM_SEARCH`，回到 `AUTO_AIM_TRACK`。

## 4. 建议数据流

```text
                Remote / Vision / Referee
                         │
                         ▼
               Command / Behavior Layer
                决定当前工作状态
                         │
             ┌───────────┴───────────┐
             │                       │
        AUTO_AIM_TRACK          AUTO_AIM_SEARCH
             │                       │
      Vision target          Search Planner
      yaw / pitch             scan_update(dt)
             │                       │
             └───────────┬───────────┘
                         ▼
                    GimbalCommand
                         │
                    CommandRouter
                         │
                     gimbalTask
                         │
                     GimbalAxis
                         │
                     Motor / PID
```

Safety 不属于某个搜索状态，而是横跨整条链路，对最终命令拥有否决权。

## 5. 扫描轨迹建议

结合目前计划中的“大 Yaw 360° + 小 Yaw 有限位 + Pitch 有限位”结构，推荐分阶段实现。

### 阶段 A：只做大 Yaw 基础巡航

在基本功能验证完成后的第一版，只实现最简单、最容易验证的搜索：

```text
大 Yaw：持续低速单方向 360° 旋转
小 Yaw：保持中位
Pitch ：保持中位
```

大 Yaw 可直接使用 `GimbalMode::Rate` 输出固定低速角速度。

优点：

- 不需要处理角度跨 ±π 的折返问题；
- 不需要搜索轨迹状态机；
- 可以先验证自动命令抢占、Safety 打断和视觉重获目标后的切换。

### 阶段 B：加入小 Yaw / Pitch 往返扫描

基础巡航稳定后，再增加有限位轴的三角波式往返：

```text
small_yaw_target += small_yaw_dir * small_yaw_rate * dt
pitch_target     += pitch_dir     * pitch_rate     * dt

到达上限 -> dir = -1
到达下限 -> dir = +1
```

建议：

- 小 Yaw 扫描速度低于大 Yaw；
- Pitch 更慢，避免画面持续上下抖动；
- 小 Yaw 和 Pitch 不要同时在端点反向，可错开相位；
- 所有范围首先使用保守软限位，实际数值通过机械测试确定。

### 阶段 C：搜索体验优化

最后再考虑：

- 丢目标延迟进入搜索，避免短暂识别丢失导致频繁切状态；
- 重获目标连续若干帧后确认 Track；
- 以最后一次目标方向为搜索中心；
- 根据底盘运动状态动态改变巡航速度；
- 视场覆盖优化，而不是固定机械波形；
- 搜索状态与自瞄、导航策略联动。

这些都不属于第一版必须功能。

## 6. 推荐模块边界

### 6.1 CommandManager / Autonomous Producer

负责：

- 判断是否允许自动模式；
- 判断视觉目标有效性和新鲜度；
- 选择 `TRACK` 或 `SEARCH`；
- 处理手动接管优先级；
- 输出最终高层云台命令。

不负责：

- PID；
- 电机生命周期；
- 硬限位保护；
- CAN/UART 发送细节。

### 6.2 Search Planner

后续建议新增一个纯逻辑模块，例如暂定：

```text
include/robotics/gimbal/gimbal_search.hpp
lib/robotics/gimbal_search.cpp
```

它只保存搜索轨迹自身状态，并生成云台目标，不直接访问电机。

概念接口：

```cpp
struct GimbalSearchConfig {
    float big_yaw_rate_rad_s;
    float small_yaw_min_rad;
    float small_yaw_max_rad;
    float small_yaw_rate_rad_s;
    float pitch_min_rad;
    float pitch_max_rad;
    float pitch_rate_rad_s;
};

class GimbalSearchPlanner {
public:
    int reset(/* 当前云台反馈 */);
    int step(float dt_s, GimbalCommand &out);
};
```

名称和接口只是实施参考，等当前云台结构稳定后再最终确定。

### 6.3 CommandRouter

预计**不需要增加巡航语义**。

它继续只做：

```text
RobotCommand -> 本地云台命令 / 板间命令
```

这样后续无论命令来自遥控、自瞄、巡航还是导航，Router 都不需要跟着增加行为逻辑。

### 6.4 Safety / GimbalAxis / Motor

原则上不因巡航功能修改职责：

- Safety 只检查“能不能执行”；
- GimbalAxis 只检查/执行轴命令；
- Motor/PID 只做闭环。

搜索命令必须像普通命令一样接受 Safety 限制，不能绕过现有保护链路。

## 8. 开始实现前的前置条件

先完成并确认以下基本功能，再开始巡航：

- [ ] 遥控输入 -> `CommandManager` -> 云台的手动控制稳定；
- [ ] 大 Yaw 基础位置/速度控制稳定；
- [ ] 小 Yaw、Pitch 基础控制和机械软限位确定；
- [ ] 全局 Safety 的 Disabled / Hold / Active 行为验证；
- [ ] 本地云台 Safety 可在异常时可靠阻断输出；
- [ ] 电机掉线、恢复、命令超时行为验证；
- [ ] 视觉 UART/协议解析稳定；
- [ ] 能可靠判断视觉“有目标 / 无目标 / 数据过期”；
- [ ] 自瞄 yaw/pitch 命令的坐标系与单位已经固定。

## 9. 第一轮功能测试建议

巡航真正实现时，第一轮只测试阶段 A：

1. 自动模式、无目标 -> 大 Yaw 低速转圈；
2. 搜索过程中切手动 -> 立即由遥控接管；
3. 搜索过程中 Safety Hold -> 云台保持；
4. 搜索过程中 Safety Disabled -> 输出失能；
5. 搜索过程中出现有效视觉目标 -> 停止巡航并进入 Track；
6. Track 丢目标超过设定时间 -> 恢复 Search；
7. 视觉数据过期不能被当作有效 Track 命令；
8. 搜索状态不得触发任何默认开火行为。

测试初期建议：发射机构物理断开或保持禁用，大 Yaw 使用明显低于正常巡航速度的限速参数。

## 10. 参考的开源项目结构倾向

前期调研中比较有代表性的项目：

- Meta-Team/Meta-Embedded-NG：自动哨兵入口放在 `application/cmd/auto_cmd.c`，云台接收上层生成的目标；
- HDU-PHOENIX/Sentry-Embeded-2026：整车 Command/状态机管理自动行为，云台控制层执行；
- Hello World 哨兵相关协议：常见优先级思路为自瞄/决策命令优先，默认巡航作为无高优先级目标时的行为。

共同点不是具体函数名，而是：**搜索是行为层问题，不是 PID 问题。**
