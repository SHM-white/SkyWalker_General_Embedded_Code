## 1. 当前结论与已确认条件

用户确认：CAN1 接 GM6020，CAN2 接 M3508，两台都是 ID3，每条 CAN 只接一个设备，单独控制正常。`board_config.hpp` 与这个配置一致；`dual_speed.cpp` 的 ID2 启动文字及 `app.overlay` 的旧端口注释已经过时，不能按这些文字判断实物接线。

本次捕获的直接故障链是：

```text
RUN 104903 ms
  → CAN2/3508 在 105964 ms 发送目标帧 0x200 时 Bus-off
  → 发送回调 -114，TransportError，Group 撤销两台电机输出
  → 主循环在 105969 ms 记录 STOP transport -115
  → CAN1/6020 同一毫秒发送安全输出 0x1fe 也报 Bus-off
  → 总线恢复，反馈继续更新，但位置参考失效
  → 后续重新解锁出现 STOP enable -61
```

从 RUN 到 STOP 是 **1066 ms**。这一次的直接触发不是代码中的 1000 ms 使能等待超时：已经出现 RUN，而且 STOP 原因是 transport。两路都出现通信异常，不能仅凭首先报告的 source=3508 判定 3508 损坏。

**尚未确定**为何双路工作引起底层 CAN 错误。单独控制正常是重要对照，但不同样例仍可能有启动、并发、时钟、外围设备与发帧节奏差异，不能据此直接认定是某个共享资源缺陷。

停止后，两路反馈保持 fresh=1，温度约 26–27°C，程序周期约 5.1 ms。CAN2 的 CRC/form 计数仍增加：设备时间 150477 ms 时为 34/24，215675 ms 时为 114/68，期间最新恢复记录仍为 count=5、105964 ms。因此不应把全部错误增长解释成每次运动启动瞬间的现象。

这些统计不能证明具体哪根线或哪个外设损坏。尤其 `bit0` 不能直接当作失败帧数：M_CAN 在 Bus-off 恢复过程中也会用 Bit0Error 标示恢复序列。参见 [Bosch Busoff Recovery Handling](https://www.bosch-semiconductors.com/media/ip_modules/pdf_2/m_can/m_can_an004_v1-0_busoff_recovery_handling.pdf)。

## 3. 错误码与代码路径

| 字段 | 本项目含义 | 依据 |
| --- | --- | --- |
| fault/reason=8 | TransportError | `include/drivers/motor/motor.hpp` |
| bus=1 / bus=2 | Running / Recovering，软件总线状态 | `include/drivers/motor/can_bus.hpp` |
| hw=2 / hw=3 | Error Passive / Bus-off，硬件状态 | Zephyr `include/zephyr/drivers/can.h` |
| -114 | -ENETUNREACH | 本地 Zephyr `lib/libc/minimal/include/errno.h` |
| -115 | -ENETDOWN | 同上；应用 transport 分支主动填写 |
| -61 | -ENODATA | 同上；当前缺少所需有效数据 |
| purpose=0 / purpose=1 | Target / SafeOutput | `include/drivers/motor/can_bus.hpp` |

不能用 Linux 主机 errno 数值解释板端 -114。本地 M_CAN 驱动在 Bus-off 时用 -ENETUNREACH 回调待发送帧，项目 `CanBus::processTx()` 收到后调用 `enterRecovery()`，保存重启前状态并通知电机故障。其语义与 [Zephyr CAN API](https://docs.zephyrproject.org/latest/doxygen/html/group__can__controller.html) 一致。

`dual_speed.cpp` 的 `stop("transport", -ENETDOWN)` 是后续应用判断，因此排查根因要看 `group_fault` 和 `pre_restart`，不能只看 STOP 的 -115。`pre_restart` 发生在软件重启前，但不一定在硬件自动恢复动作前；其中 TEC=0 不能否定 Bus-off。

原先文档 [舵轮零指令停机现场](舵轮零指令停机现场.md) 记录的是 CAN2 接 6020 的旧现场；本次 CAN2 接 3508，首先记录 Bus-off 的仍是 CAN2。这提高了对 CAN2 通道及双路运行条件的关注，但旧现场与本次并非严格控制变量实验。

## 4. 可以具体修正的后续使能问题

涉及文件按执行顺序：

1. `drivers/motor/motor.cpp` 的 `Motor::raiseFault()`：通信故障会置 `position_reference_valid=false`。这是现有保护语义，应保留。
2. `lib/control/motor_control.cpp` 的 `PositionMotor::reset()`：参考无效时返回 -ENODATA；这个函数只重置控制器，不能重建已经丢失的连续位置坐标。
3. `samples/robotics/swerve/src/dual_speed.cpp`：重新解锁分支直接 `steer_axis.reset()`，没有先重建参考。日志把 reset 和真正 enable 的错误统称为 enable，降低了可诊断性。

因此源码解释了后续 -61。当前 STOP 没有打印反馈有效位及失败的具体 reset 阶段，建议先补齐这些字段，让下次日志直接确认。

手动修改建议，仅用于此 StartupRelative 往复诊断样例：在已有 `!engaged && rc.run_allowed`、`group.ready()` 成功的分支内，替换原 reset/enable 小段。当前样例明确定义每次人工解锁捕获新的往复中心，因此可把解锁时当前位置重新定义为零。正常完整底盘绝对坐标控制不能照搬这个选择。

```cpp
const char *operation = "6020_reset";
ret = 0;
const auto view = steer.snapshot();
if (!view.position_reference_valid) {
    operation = "6020_reseed";
    ret = steer.reseedPosition(0.0);
}
if (ret == 0) {
    operation = "6020_reset";
    ret = steer_axis.reset();
}
if (ret == 0) {
    operation = "3508_reset";
    ret = drive_axis.reset();
}
if (ret == 0) {
    operation = "group_enable";
    ret = group.enable();
}
if (ret < 0) stop(operation, ret);
else { engaged = true; enable_ms = now; }
```

这段建议只处理通信恢复后的重新使能，**不能修复首次 Bus-off**。不要放到每周期无条件执行，也不要在故障后自动重启运动。

`Motor::reseedPosition(double known_position_rad)` 的参数单位是输出轴弧度；0 表示显式建立当前相对零点。返回 0 后更新反馈位置、设置参考有效并递增参考代数。Active/Enabling 返回 -EBUSY，反馈不新鲜返回 -EAGAIN，参数非法返回 -EINVAL，能力不支持返回 -ENOTSUP，代数溢出返回 -EOVERFLOW。内部使用电机锁；这里应在主循环线程、停机后人工重新授权的路径调用。后续 reset/enable 仍检查各自前提，任何错误必须退出本次使能。

可参考 `samples/robotics/swerve/src/main.cpp` 的 `reseedPosition` 调用理解恢复流程；该完整样例使用绝对舵角，不能把其坐标选择和本诊断的相对零点混用。3508 是速度控制，本段无需为它补位置参考。

同时手动在 `logMotor()` 增加 `feedback.valid`、`position_reference_valid` 和 `reference_generation`；将 ID2 日志和过时接线注释改成当前实际配置或从配置对象取值。保留原始故障记录，避免恢复后的零计数覆盖证据。

## 5. 首次 Bus-off 的下一步隔离顺序

用户已确认各自单独控制正常，下一步应保持当前固件外围配置，只改变运行方式，避免重复泛查接线或改 PID。

| 场景 | 保持条件 | 要回答的问题 |
| --- | --- | --- |
| 当前工程只运行 CAN1/6020 | 时钟、遥控、USB、日志、5 ms 周期相同，使用零电流 | 已知单路正常能否在同一工程条件下重现？ |
| 当前工程只运行 CAN2/3508 | 同上 | 区分通道差异与样例差异 |
| 当前工程双路零电流 | 两路都发送，保留保护 | 不发生运动时双路是否也失败？ |
| 双路零电流错开发送 | 每路仍为 5 ms，第二路错开约半周期 | 若改善，继续定位时间重叠、调度及共享资源 |

这是供用户后续实施的诊断方案，本轮没有实现或执行上述新场景。单路版本必须同步改为单成员 Group/单轴控制与对应状态检查；仅注释一路 commit 会人为引入 CommandExpired，失去比较意义。原始相邻两次 commit 只是向各自 I/O 工作线程发布，不等于硬件发送已经严格串行；错开方案必须保持每路自己的更新/commit 节奏。

每个场景从相同启动状态开始，记录首次恢复前的硬件状态、错误增量、帧 ID/用途及时间。每次仅观察到首次故障或预定的相同时间窗口，不自动反复重启电机。若同工程单路稳定而双路零电流失败，再有针对性地查共享 CAN 时钟/复位、消息 RAM 与驱动并发。已有 `../build/swerve_rc/zephyr/zephyr.dts` 的两路 RAM 起始偏移分别是 0 和 0x350，没有看到相同起始地址；这只是已有构建文件，不能当作本次实机寄存器证明。

若需要示波器对照，应同时关注两路总线波形与收发器电源，比较单路/双路差异。换线或调整硬件应断电；上电前保持人工停机状态、固定并悬空运动部件，逻辑反馈稳定后才人工授权。本轮未确定终端电阻值，也没有根据这一缺失信息判定接线错误。

完成全部手动代码修改后，可在既有 Zephyr 环境仅做一次构建；此处不替用户运行：

```sh
west build -b dm_mc02/stm32h723xx samples/robotics/swerve -d ../build/swerve_dual_diag
```

预期：若仅做参考恢复补充，Bus-off 后仍会安全停机；总线恢复且人工再次解锁时，不再卡在缺少位置参考的 -61。首次 Bus-off 是否消失必须由隔离场景重新判断，不能把“能重新启动”当作通信根因已解决。
