# 双主控框架使用说明

这次已实现业务源码。两块主控均使用达妙 MC02，application 和 samples 是独立的 Zephyr 工程，共享的只有 `include/`、`lib/`、`drivers/` 中的正式模块。旧 `application/` 占位入口保留，新应用放在 `applications/`。

## 构建与配置入口

| 工程 | 硬件配置 | 算法、超时与运行配置 |
| --- | --- | --- |
| 云台主控 | `applications/sentry_gimbal/app.overlay` | `applications/sentry_gimbal/src/board_config.hpp` |
| 底盘主控 | `applications/sentry_chassis/app.overlay` | `applications/sentry_chassis/src/board_config.hpp` |
| 独立上机项目 | 各 sample 的 `app.overlay` | 各 sample 的 `src/board_config.hpp`，或原电机 sample 内的参数 |

从仓库根目录运行：

```sh
west build -b dm_mc02 applications/sentry_gimbal -d build/sentry_gimbal
west build -b dm_mc02 applications/sentry_chassis -d build/sentry_chassis
# 接好调试器、选定要刷的主控后，分别执行：
west flash -d build/sentry_gimbal
west flash -d build/sentry_chassis
```

两个应用默认 `connections_configured=false`，电机节点为 `disabled`；这时通信与诊断线程仍运行，输出域报告 ConfigBlocked。按实际接线调整 overlay、启用电机节点、确认控制参数后，把对应应用的 `connections_configured` 改为 `true`。这是机器人装配配置开关，samples 的配置不参与应用构建。

默认板间候选接口为 USART1：PA9 TX、PA10 RX，460800 baud、8N1；双方交叉 TX/RX 并共地。主控控制台使用 MC02 原板配置 USART10，115200 baud。实物端口以你的板卡接线为准。云台应用未默认绑定遥控和裁判，需添加 `remote-uart`、`referee-uart` aliases；串口必须具备独立的 DMA RX/TX 设置，不能复用已占用 DMA 通道。

DR16 的 UART5/8E1/DMA 配置可参考独立 DR16 sample；裁判的独立 USART1 配置可参考 referee sample。复制需要的配置到本应用，不引用 sample 文件。板间口与裁判不能同时占同一个 UART，USART2/3 在 MC02 板 DTS 中属于 RS485 配置，修改前确认电气连接与 DE。

云台支持选择 DJI / DM 后端，但位置能力必须匹配：Continuous 使用 `AbsoluteNearest`，后端必须声明固定零点单圈反馈；不支持该能力的 DM 型号/模式会明确返回 `-ENOTSUP`。Limited 使用校准后的 `DriverContinuous`，机械限位、编码器零点必须与该坐标一致。不能将失联期间不可观测的圈数视作已知。

底盘模板为 CAN1 上 4 个 GM6020 舵向 + 4 个 M3508 驱动。顺序固定 FL、FR、RL、RR，分别修改电机 ID、减速比、装配零点、轮径、位置 `(x_m,y_m)` 与正负方向。GM6020 必须确认使用电流控制协议。硬件适配器按 `Descriptor::can` 自动分组为 1 或 2 个共享 Bus，检查同一 CAN 内的重复反馈 ID、发送槽冲突、能力和电流上限；不同 CAN 可使用相同 ID，第三条 CAN 返回 `-ENOTSUP`。将四个 drive 节点的 `can-bus` 改为 `<&can2>` 即可选择舵向 CAN1 / 驱动 CAN2，八个 alias 和控制算法配置不变；也支持其他两 CAN 分配。默认仍为单 CAN 模板。

## 运行数据流

```text
DR16 UART -> RemoteService -> RemoteState -> ManualCommandMapper
裁判 UART -> RefereeParser -> 分字段许可/功率额度
                       -> GlobalSafetyManager -> CommandManager
                       -> CommandRouter
                          + 本地完整快照 -> GimbalLocalSafety -> YawGimbal
                          + 远端完整快照 -> InterBoardCodec / AsyncUart
底盘 UART -> InterBoardLink -> ChassisLocalSafety -> SwerveChassis
                                                 -> ChassisPowerLimiter
                                                 -> DjiChassisHardware -> DJI Bus × 1/2 -> 八电机
```

应用使用自身的 `Latest<T>` 短临界区值拷贝；纯算法和解析器不依赖这些通道，也不依赖 zbus。路由两个出口分别返回提交结果，一方忙不跳过另一方。连续状态覆盖旧值，不积压历史轨迹。独立事件（射击、保存零点等）尚未开放执行；Auto 未配置生产者时输出禁用。

云台任务：遥控、裁判、板间通信、100 Hz 命令、200 Hz 云台；底盘任务：板间通信、200 Hz 控制。通信任务独占本 UART 的 RX/TX，ISR 只复制字节及管理缓冲。周期为初始配置，实际 CAN 耗时和调度延迟需测量；日志为限频诊断。

## 电机生命周期

正常顺序是 `configure -> poll -> resume -> update`。临时异常后 `suspend -> poll -> resume`，对象、CAN 所有权和回调保留；`stop` 只用于主动终止。

| 操作 | 语义 |
| --- | --- |
| `configure()` | 仅一次配置/绑定，校验单位、能力和限幅；成功进入 Waiting，不等待电机供电 |
| `poll(now_ms)` | 单所有者线程推进准备；0 表示 Ready，负值记录原因并继续周期调度，不 arm |
| `resume()` | 调用方已验证当前许可和新命令后调用；再次读取反馈、重置 PID 与参考，再确认零输出并进入 Active |
| `update(target)` | 使用实际 dt 执行已有 C 控制内核；错误撤销输出，进入可恢复等待 |
| `suspend(reason)` | 幂等撤销软件目标；保留首次原因/零帧结果；EmergencyStop 才锁存 |
| `clearEmergencyStop(released)` | 未解除输入返回 `-EBUSY`；解除并显式复位后回 Waiting，不自动沿用目标 |

`begin()` 保留兼容入口：最多等待约 3 秒并尝试 arm。它不是应用启动路径；正式应用和更新后的四个 wrapper samples 使用 configure/poll。第三方后端若只实现旧 prepare，默认适配仍可能阻塞；实现新的 configure/pollPrepare 契约才能获得同样的周期准备语义。

默认反馈稳定窗 30 ms；等待握手阶段每 5 ms 轮询，实际发送/读反馈失败后每 100 ms 重试，永不耗尽重试次数。DM 禁用态可能只响应主机探测，因此准备阶段发送有限频率的 Disable；故障清除有 ClearError、Disable、等待新反馈三步，丢失回复后重新探测。功率许可明确禁止时，应用不调用准备/使能路径。

`MotorStatus` 包含当前状态、原因、首次运行错误、最后恢复结果、零输出错误、恢复 generation、重试统计。不能把累计计数当永久禁止条件。

DJI 重新准备时以新编码器反馈重播种连续坐标：有固定零点的 1:1 轴使用绝对角，无固定零点的轴重新从零建立相对坐标；DM 按协议 PMAX 重建展开基准。位置环、速度环和轨迹参考随恢复重置。

底盘所有 Bus 都 arm 成功且确认零输出后，整个 hardware 才 armed。每轮 flush 覆盖所有 Bus，任意失败都会 suspend 全部；stop 遇到错误仍继续尝试剩余 CAN 并返回首个错误。恢复也轮询全部 CAN，任一失败时整体保持 not ready/not armed，全部恢复后再检查八电机反馈、重置测量基准并等待稳定窗。`busCount()` 仅供诊断，控制层不按 CAN 分别使能。

Bus 发送使用持久回调上下文和 2 ms 完成等待。超时后停止 CAN 控制器以撤销在途帧，确认撤销后才能重新发送；MC02 的 M_CAN stop 会保留 RX filter，并完成被撤销发送的回调。控制器 stop/start 的驱动耗时另计；DM arm 仍含最多约 100 ms 的使能确认等待，发生在本电机所有者任务中，其他任务继续运行。当前没有实测这些耗时。

## 板间会话与有效期

V1 与施工规格一致：A5 5A、版本 1、角色、消息 ID、负载长度、帧序号、负载、CRC16，最大 142 B；逐字段小端编码，CRC 为非反射 0x1021 / 初值 FFFF / xorout 0。支持 Heartbeat、ChassisControl、ChassisConstraint、ChassisFeedback 四种消息，其余消息丢弃并计数。

每种消息独立检查帧序号；运动有效期只由命令生产者的 `command_sequence` 前进刷新。重发同一目标、收到心跳、转发裁判其他字段，都不延长旧命令或旧许可的有效期。CRC 错误保留上一条尚未过期的合法状态。解析器重新同步后仍保留原字节到达时刻，不把解析延迟算作新接收。

每板从硬件 RNG 获取 boot ID。底盘完成一次硬件恢复并重置四轮算法后递增 generation，向云台发布 Ready。云台 command_task 重新从当前输入产生命令并回显 boot ID/generation。底盘等待同一上下文连续 3 条新命令再 arm；重复握手不会不断增加 generation。云台在本地重新准备后也等待恢复边界后的命令。

心跳与命令分别参与安全判定，不互相刷新有效期。底盘使用收到的 `BoardHeartbeat.stamp`（本地接收时刻），默认 100 ms 超时后本地 Disable、报告 `TransportUnavailable` 并清空稳定计数；心跳恢复后，重复旧 producer sequence 不会计数，必须重新收到 3 条新命令才能 arm。掉线期间见过的命令也不能作为恢复后的第一条。硬件恢复时仍会递增 generation 并重新对齐命令上下文。

云台 GlobalSafety 默认分别以 100 ms 检查底盘心跳和反馈；心跳失效、反馈过期或底盘 Waiting/Recovering/ConfigBlocked/EStopLatched 时只禁用 chassis。健康的小 Yaw 继续按本地/全局许可执行，全局显示 Degraded；Waiting/Recovering 即使 reason 为 0 也不会被误报为全车 Active。Ready/Active 只放行原先的底盘许可，不覆盖遥控、裁判或急停策略。全局急停仍锁存并禁用所有输出。底盘本地急停会进入全局诊断 reason，但 application 路由前移除非全局急停的 EmergencyStop 请求位，避免旧协议把诊断回送成新急停而使底盘无法本地复位；全局决策和日志保留该诊断。

UART 中断、接收溢出或 RX 停止后解析器丢弃残缺片段，通信任务重新启用接收；TX 缓冲在 DONE/ABORTED 前不复用。UART TX deadline 超过后发起 abort，等待回调归还缓冲。

显式急停通过 `board_config.hpp` 的输入/复位 hooks 接入；云台急停原因随命令传播使底盘锁存。当前没有跨板复位事件协议，因此底盘的明确复位需要接入本地 reset hook。RC Safe 是普通禁用，不是急停。

## 裁判与功率

两个应用默认要求裁判许可；台架上可显式将各自的 `require_referee_for_motion` 设为 false。即使台架模式，收到有效裁判禁止后仍执行禁止，已知许可超时也暂停。

裁判解析器默认版本 Unspecified，只统计帧、不解释许可；目前已实现可显式选择的 `Rm2026V1_3`。该版本的 0x0202 前 8 字节为保留字段，不能当作功率测量；0x0201 许可和额度、0x0202 缓冲各自维护更新时刻。依据 [RoboMaster 2026 通信协议 V1.3.0 第 13～14 页及 CRC 附录](https://bbs-web-static.robomaster.com/ef4f084944e34393aa70378a4a405c681774586313231/RoboMaster%202026%20%E6%9C%BA%E7%94%B2%E5%A4%A7%E5%B8%88%E9%AB%98%E6%A0%A1%E7%B3%BB%E5%88%97%E8%B5%9B%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE%20V1.3.0%EF%BC%8820260327%EF%BC%89.pdf)。

`ChassisPowerLimiter` 是缓冲储能辅助的电流缩放初版；不等同于已经标定的比赛功率控制。底盘配置提供 `idle_power_w`、`power_per_abs_amp_w` 和 `power_model_calibrated`，可用实际测量拟合估算模型。默认未标定时比赛配置禁止底盘输出，台架配置使用 `bench_effort_scale`。底盘摘要的速度与功率有效位不会把未实现的里程计/未测量的功率伪装成有效零值。

本次涉及的 Safety 输入最终定义如下；`GlobalSafetyDecision`、`LocalSafetyDecision` 和 evaluate/clearEmergencyStop 的函数签名保持不变。

```cpp
struct GlobalSafetyInputs {
    std::uint64_t now_ms = 0;
    bool command_source_fresh = false, operator_motion_enabled = false, emergency_stop_requested = false;
    OutputPermission gimbal_power{}, chassis_power{}, shooter_power{};
    MessageStamp chassis_heartbeat_stamp{}, chassis_feedback_stamp{};
    ExecutionState chassis_execution_state = ExecutionState::Waiting;
    std::uint32_t chassis_active_reasons = 0;
};
struct LocalSafetyInputs {
    std::uint64_t now_ms = 0, receiver_boot_id = 0, command_boot_id = 0;
    std::uint32_t resume_generation = 0, command_generation = 0;
    MessageStamp peer_heartbeat_stamp{}, command_stamp{};
    SafetyAction global_action = SafetyAction::Disable;
    bool power_allowed = false, feedback_fresh = false, hardware_ready = false, armed = false;
    bool config_valid = true, emergency_stop_requested = false;
};
// ChassisLocalSafety::Config
struct Config {
    std::uint32_t command_timeout_ms = 100, heartbeat_timeout_ms = 100, stable_command_count = 3;
};
// GlobalSafetyManager::Config
struct Config {
    bool require_referee_for_motion = false;
    std::uint32_t permission_timeout_ms = 300;
    std::uint32_t chassis_heartbeat_timeout_ms = 100, chassis_feedback_timeout_ms = 100;
};
```

所有超时和稳定计数须大于 0，否则 evaluate 返回 `-EINVAL`，不提交新的 decision。正常判定返回 0，是否允许输出由 decision.action 决定。时间单位为 ms，freshness 使用本地接收时间，边界为 `age <= timeout`。GimbalLocalSafety 不检查 `peer_heartbeat_stamp`。两应用和 sample 均改为配置字段显式赋值。

`DjiChassisHardware` 保留原构造函数、`init()`、`read(ChassisFeedback&)`、`suspend()`、`pollRecovery(uint64_t)`、`arm()`、`apply(const ChassisOutput&, float)`、`ready()`、`armed()`、`estimatedPowerW()`；新增：

```cpp
public:
    static constexpr std::size_t kMaxBuses = 2;
    std::size_t busCount() const;
private:
    int findOrCreateBus(const device *can);
    int stopAllBuses();
```

`busCount()` 返回已初始化 Bus 数，成功 init 后为 1 或 2。`findOrCreateBus()` 返回索引或负错误码，空 CAN 为 `-ENODEV`，第三条 CAN 为 `-ENOTSUP`，Bus 初始化失败不增加计数。`stopAllBuses()` 尝试所有 Bus 并返回首个错误，全部成功返回 0。`pollRecovery()` 返回 0 表示整个底盘 Ready，`-EAGAIN` 表示继续等待，其他负值为恢复故障；`arm()` 在任一 Bus 出错或未确认零输出时停止全部 Bus。所有生命周期操作仍由底盘控制任务串行调用。

状态迁移和单/双 CAN 数据流见前面的“运行数据流”“电机生命周期”“板间会话与有效期”。其中 heartbeat stale 直接进入 Waiting/Disable；恢复后先经过 Ready/RecoveryBoundary，再由 3 个新 producer sequence 放行 Active。上报执行状态保留本地 Safety 的 Waiting/Recovering，不用 hardware.ready 覆盖心跳故障；arm/apply 失败后不会继续上报 Active。
