## 1. 建议先做什么

当前最需要的是一条能重复走通的上车路径：**固定实车配置 → 建立随时能看的诊断出口 → 独立模块入口 → 单板组合 → 跨板组合 → 整车**。先让每次烧录只回答一个明确问题，再逐步增加参与的模块。

优先落地三件事：

1. 给另一套底盘的开发者一份可独立使用的板间接口契约，把速度所属机构、轴侧、单位、正方向、换算责任和停止语义说清楚。
2. 按实车接线统一云台板、底盘板的配置来源，让模块程序和最终整车程序使用同一套硬件参数；上车时不再为换 sample 改线、改 ID、复制 PID。
3. 每个上车阶段有独立工程、独立 `main.cpp`、固定构建产物。去掉“相同入口 + 角色宏/场景宏/额外 conf 生成不同应用”的工作方式。

不需要等全部重构完成再上车。第一批只覆盖“诊断、遥控、头部 IMU、小 Yaw、Pitch、板间观察、大 Yaw”；先把昨晚最难定位的云台链路拆开，随后推进舵轮和其他功能。

## 3. 板间协议：先把物理含义交代清楚

### 3.1 当前速度字段到底是什么

当前统一帧版本为 **v4**。消息定义见 [interboard.hpp](../../include/robotics/messages/interboard.hpp)，字节编码见 [interboard_codec.cpp](../../lib/communication/interboard_codec.cpp)。下表的偏移从 payload 第 0 字节开始，速度字段按当前 codec 使用小端 float32；不是整帧偏移。

| 消息/字段 | payload 偏移 | 当前代码对应的物理量 | 接收端应负责什么 |
| --- | --- | --- | --- |
| `0x0101 ChassisControl.vx_m_s` | 4 | 底盘车体前后方向的线速度目标，m/s | 底盘端完成运动学和轮速换算 |
| `0x0101 ChassisControl.vy_m_s` | 8 | 底盘车体横向线速度目标，m/s | 同上 |
| `0x0101 ChassisControl.wz_rad_s` | 12 | 底盘车体偏航角速度目标，rad/s | 底盘端分配到各舵轮；与大 Yaw 请求独立 |
| `0x0402 BigYawRequest.target_rate_rad_s` | 4 | 大 Yaw 关节侧角速度目标，rad/s | 大 Yaw 执行端转换到自身电机接口侧速度 |
| `0x0403 BigYawFeedback.actual_rate_rad_s` | 4 | 换算回大 Yaw 关节侧的实际角速度，rad/s | 按实际测量、正确符号和传动比返回；不能回填目标速度 |

明确结论：`0x0101` 传的不是轮电机转子 rpm；`0x0402` 传的不是原样电机转子速度，也不是小 Yaw 速度。大 Yaw 这里控制的是机械关节相对其支撑侧的转动，不能直接当作头部 IMU 的对地 yaw 角速度。

当前大 Yaw 执行器实现如下，来源为 [big_yaw_executor.cpp](../../lib/robotics/big_yaw_executor.cpp)：

```text
电机接口侧目标 rad/s = 线上的关节目标 rad/s × motor_to_joint_ratio × direction
线上的实际关节 rad/s = 电机接口侧反馈 rad/s × direction ÷ motor_to_joint_ratio
```

`motor_to_joint_ratio` 必须定义为“当前 Motor API 所代表的轴 / 大 Yaw 关节轴”的速度比。这里特意使用“电机接口侧”：不同电机驱动可能已经完成了内部减速换算，不能看到“电机”两个字就再次乘厂家内部减速比。当前大 Yaw profile 将中央 `big_yaw.gear_ratio` 传入该参数，现值为 1；它是否符合实车传动，仍需现场确认。

举例仅用于双方对单位，不作为实车参数：若电机接口轴到关节轴减速比为 6，符号为 +1，收到 `+0.2 rad/s`，则接口侧目标为 `+1.2 rad/s ≈ 11.46 rpm`；反馈也必须除以 6 后回传。若接口反馈已经是关节轴速度，这一层比值应为 1。

对轮驱动则应写清完整链路：

```text
车体 vx、vy、wz → 各轮位置处的速度 → 舵角和轮缘线速度
轮轴 rad/s = 轮缘 m/s ÷ 轮半径 m
转子 rpm = 轮轴 rad/s × 转子到轮轴总减速比 × 60 / (2π)
```

实际控制若已使用输出轴单位的 DJI API，就使用轮轴速度，不再重复乘减速比。当前 DJI 文档明确 `velocity_rad_s` 是输出轴速度，见[电机单位说明](../modules/drivers/motor-dji.md)。符号变换同样只能在约定的一层完成。

### 3.2 正方向和坐标系要单独约定

建议把底盘坐标约定固定为 X 前、Y 左、Z 上，正 yaw 按右手规则，从上向下看为逆时针，并在实车上贴方向标识。当前底盘运动学使用 `vxi = vx - wz·yi`、`vyi = vy + wz·xi`；另一套底盘的坐标和安装符号尚需对照。

大 Yaw 需要额外写清“从哪里看为正”、关节轴与电机轴的关系，以及反馈是否同向。**当前云台启用了 `CONFIG_VEHICLE_BIG_YAW_REVERSE=y`**，发送请求前反号、接收实际反馈后也作对应转换，见[当前云台说明](../../applications/sentry_gimbal/README.md)。这说明线上方向包含当前对端的适配约定，不能直接宣布它已经等于上述统一物理正方向。

落地时为每套底盘适配填写一张小表：线上正方向、驱动反馈轴、内部减速是否已处理、外部传动比、安装符号、换算所在文件。先冻结双方一致的现有线协议；以后统一方向时同步改双方适配和契约版本，禁止一端悄悄改符号。

### 3.3 对外协议文档需要补齐的内容

建议后续新增 `docs/protocols/interboard-v4.md` 作为另一套程序也能直接使用的规范；现有[通信说明](../modules/communication/communication.md)和[传输说明](../modules/communication/interboard-transports.md)链接到它。本次不直接修改这些文件。

规范至少包含：

- 完整帧头、CRC 参数及覆盖范围、每个 payload 的长度/偏移/类型/枚举值；明确小端、浮点格式和保留字节要求。不能要求对方按 C/C++ 结构体内存布局猜。
- 上述物理量表、正方向图、换算例子；注明 `ChassisMode::Spin` 对平移分量的处理，不能只列字段名。
- 必须实现的消息集合。大 Yaw 联调至少涉及心跳、操作授权、请求和反馈；底盘行走再接行走命令/状态，实际约束模式再接裁判约束。
- 消息周期、接收超时、原始输入年龄、命令年龄、状态生产年龄、boot 绑定、通信序号与生产序号的区别。当前大 Yaw 执行器默认命令与来源时限为 100 ms、权限时限为 300 ms；具体值应随固定配置记录，不能拿“心跳在线”代替命令有效。
- `Disabled + 0` 表示失能；`FollowCenter + 0` 是启用速度控制下的零速请求，两者不等价。停机、断流、对端重启和重新解锁分别怎么处理。
- 同一生产序号可被新的传输帧降为停止，但不能借重发刷新年龄或恢复运动；无效反馈必须有 valid/age，不能伪装成真实零速。
- 固定输入和预期字节的对照样例：正/负速度、零速、Disabled、无效反馈、超时与重启。发布规范时从当前 codec 取得字节样本，附双方解码结果；本文不提供未经核对的十六进制帧。

注意：当前 `0x0101` 的 payload 没有与 `0x0402` 相同的原始年龄字段。必须分别说明它如何结合命令序号、接收时限和 `0x0301` 操作输入时效约束，不能把大 Yaw 的年龄机制直接描述成所有消息都有。若双方需要额外的原始命令年龄保障，应另行设计兼容升级。

已有字段的语义澄清可以先保留 v4。改变既有字段含义或布局时，应显式升级协议，不能静默复用版本号。

### 3.4 两套云台 × 两套底盘怎么联调

先登记四个组合：当前云台/当前底盘、当前云台/另一底盘、另一云台/当前底盘、另一云台/另一底盘，分别记录源码版本、协议版本、单位适配、已通过的阶段。本文无法替未读取的另一套实现判定兼容。

先以现场最稳定的组合为基线，每次替换一侧。对新组合先做无输出的协议观察，再做大 Yaw 或行走单项动作。不要同时替换两侧控制器后比较“整车效果”。旧协议如果必须兼容，转换集中在明确的板间适配边界，不散落进 PID、遥控映射和各个 sample。

## 4. 配置共用，入口独立

### 4.1 共享范围

应用和上车程序之间只共享配置，不共享整车入口、装配流程或统一的 `run(stage/role)`。已有驱动、协议、控制器和执行器继续作为普通模块 API 使用，无需复制算法库；但不能把入口换个名字挪进公共头文件，又让各个 `main()` 仅调用它。

| 层次 | 共用内容 | 明确边界 |
| --- | --- | --- |
| 实车物理配置 | 接口/引脚/DMA/波特率/CAN ID、供电、IMU 型号与模式 | 按云台板和底盘板分别定义；同一板上的所有阶段保持一致 |
| 标定与控制参数 | 减速比、方向、零点、限位、PID、周期、时效、输入映射 | 统一来源，不从其他 sample 的 `src/board_config.hpp` 引用参数 |
| 阶段策略 | 固定输出上限、允许的命令来源、观察/执行职责 | 用明确配置文件描述；模块程序可以更保守，不得覆盖真实接线与标定来“跑通” |
| 应用入口 | 对象构造、attach/start 顺序、线程、执行循环、总线提交 | 每个工程自行装配，只启动本阶段需要的模块 |

共享配置应是值、常量、配置结构或无副作用的配置构造函数，不能夹带静态电机实例、线程启动、CAN 提交和无限循环。现有 `vehicle_bench.hpp`、`chassis_bench.hpp`、`shooter_bench.hpp` 中的运行逻辑不能整体搬到一个叫 `config.hpp` 的文件中。

建议先沿用现有 `include/robotics/vehicle/` 参数，逐步抽出尚在各 sample 中重复定义的内容；物理 overlay 和基础 conf 则移到应用与 samples 都能依赖的配置目录。不要一开始引入配置生成器或新框架。

```text
config/vehicle/installed/               # 建议新建，实际接线基线
  gimbal.overlay / chassis.overlay     # 同一板各阶段共用
  base.conf                            # 通用系统选项
  gimbal.conf / chassis.conf           # 各板固定硬件驱动设置
  stages/                              # 必要的固定阶段策略值
include/robotics/vehicle/               # 沿用并补全物理参数、控制参数
applications/sentry_gimbal/src/main.cpp # 自己装配最终云台
applications/sentry_chassis/src/main.cpp# 自己装配最终底盘
samples/bringup/<具体阶段>/
  CMakeLists.txt / prj.conf / app.overlay / README.md
  src/main.cpp                         # 自己装配该阶段
```

本地 `app.overlay` 只包含对应实车物理配置；本地 `prj.conf` 只列该入口需要的模块能力等差异，不复制电机标定。共同配置由各工程构建文件固定引用。Kconfig 仍可表达驱动依赖，但不能再用 `*_CHASSIS_ROLE`、`*_LOCK_PITCH`、`*_VISION_EXECUTE` 等分支把一个入口变成多种上车应用。

一次只调一个电机时，未测试的设备可以仍在物理设备树中声明；是否实例化执行器、注册电机、启动接收线程，由该阶段自己的入口明确决定。

### 4.2 构建和产物规则

以后操作者只选择目录，不叠加 `EXTRA_CONF_FILE`、场景宏或角色参数。云台/底盘、编码器/惯性、视觉观察/执行、有载/空载分别是独立工程。需要持续使用的故障诊断程序也独立建入口，不藏在正常上车程序的自动注入宏里。

例如以下是**目标命令，目录尚未创建，当前不要照此运行**：

```sh
west build -b dm_mc02/stm32h723xx samples/bringup/gimbal_yaw_encoder -d ../build/bringup/gimbal_yaw_encoder
west build -b dm_mc02/stm32h723xx samples/bringup/gimbal_pitch_encoder -d ../build/bringup/gimbal_pitch_encoder
west build -b dm_mc02/stm32h723xx samples/bringup/gimbal_head_imu -d ../build/bringup/gimbal_head_imu
west build -b dm_mc02/stm32h723xx samples/bringup/chassis_big_yaw -d ../build/bringup/chassis_big_yaw
```

每个工程使用独立 build 目录。产物和启动日志包含应用名、板角色、源码版本、硬件配置版本、标定版本、协议版本、阶段输出上限；本地未提交修改也应注明。相同源码版本不保证配置相同。

中央标定修改后，相关阶段和整车都重新构建；已有“通过记录”按受影响的模块重新确认。配置文件共用只能避免维护漂移，不能让已烧录的旧二进制自动更新。

## 5. 通过 DAPLink 的唯一日志串口诊断

根据补充的现场条件，第一批按“只有 DAPLink 烧录器上连接的一个日志串口”设计。电脑连接 DAPLink 的虚拟串口，由 DAPLink 转接目标板 UART；不依赖目标板自己的 USB CDC，不要求第二个日志/VOFA 串口。**使用同一根串口连接，通过修改代码中的一个模式变量，再重新编译、烧录，选择文本日志或 VOFA JustFloat 数据输出。运行期间模式固定，不设计串口命令切换。**

### 5.1 先固定实际可触达资源

先登记 DAPLink 实际接入的目标板 UART、TX/RX 引脚及电气连接，并在共享物理配置中统一命名为诊断口，例如 `diagnostic-uart`。不能根据“日志串口”直接认定就是 UART7：板级 DTS 默认 console 是 USART10，当前整车云台 overlay 则改为 UART7。所有上车入口和最终应用必须跟随同一实物接线。

日志和 VOFA 都只要求目标板 TX 接 DAPLink RX，并有共同信号参考；本方案不靠串口接收命令，因此不要求为切换模式增加目标板 RX 接线。随后按实物登记连接器、当前设备、TTL/RS485/CAN 电气形式、DMA 和软件所有者。当前代码提供的候选基线如下，不等于已确认现场接线：

| 云台资源 | 当前整车用途 | 方案 |
| --- | --- | --- |
| UART5 / DBUS | 遥控 | 保留原接线；底盘调试尽量经板间取得原始授权，避免来回移动接收机 |
| USART10，PE3 TX / PE2 RX | 板间 460800；板级默认原为 console | 若 DAPLink 实际接这里，应先解决板间资源冲突，再固定双方映射；不能一口同时承担裸板间流和诊断流 |
| UART7，PE8 TX / PE7 RX | 115200 日志，另有视觉别名 | 若 DAPLink 实际接这里，则统一保留为诊断口，视觉使用其他明确资源 |
| CAN3 | 外置头部 IMU | 与当前 CAN IMU 整车配置保持一致 |
| USB CDC | 一些 sample 的遥测 | 当前不计入可用出口 |

**近期固定方案：模式变量初值为文本日志，需要调参时将变量改为 VOFA，再重新编译烧录。** 日志与波形沿用相同波特率，初始预算为 115200、8N1；更高波特率只有在当前 DAPLink 和线路确认可用后才采用。视觉和板间业务不能再占用这个诊断 UART。

以下方案保留为诊断范围扩展或链路故障时的备选，不作为第一批必须增加的接线：

| 方案 | 适用条件 | 边界 |
| --- | --- | --- |
| 板间 UART 被动监听 | 能接触板间线或预留接头 | 分别监听两个方向，适配器只接 RX 与参考地，不并接 TX；可确认线上帧，无法直接看到内部 PID 和门控 |
| SWD + RTT | 调试接口可接触，探针和固件具备相应支持 | 可作为后续独立观测出口；当前是否可用待确认，不把 RTT 写成现成功能；实时控制时不靠停核断点观察 |
| 板间带诊断消息，由可触达的一板转出 | 一侧有可用出口，双方均能修改 | 新增有界、低优先级诊断协议；控制/停止帧优先，满队列丢诊断，不能转发无限文本；另一套代码也要配合 |
| CAN 观测或迁移板间链路 | 总线资源、ID、吞吐和所有权允许 | 先画资源表；当前板间 CAN 后端独占控制器，底盘 CAN1/2/3 已分配电机，云台 CAN3 用于 IMU，不能简单切开关腾串口 |

若 DAPLink 只连一块板，该口能直接输出本板内部诊断，以及现有板间反馈已经提供的远端状态；它不能自动看到另一块板的内部 PID。需要通过同一个口查看另一板内部数据时，再增加有界板间诊断转发，标明来源板、原始年龄和有效性，并让另一套底盘实现相同接口。链路断开时远端数据必须失效，不能用最后一帧假装正常；本板诊断仍需可用。

### 5.2 每个入口统一输出什么

诊断从启动最早阶段开始工作，不等待遥控解锁、IMU 就绪、对端上线或所有电机初始化成功。初始化失败也要留下应用身份、失败步骤和错误码。

- 低频状态：例如 1 Hz，报告输入是否新鲜、请求是否有效、允许输出与否、当前阻塞原因、设备在线和 CAN 错误。
- 状态变化事件：首次失效、恢复、超时、重启、业务模式变化；附发生时间、持续时间、来源序号。避免每个控制周期打印相同错误。
- 调参数据：选择当前模块需要的少量字段，记录目标/实际值、单位、有效位、采样时间或年龄、dt、输出与饱和标志。先以 20～50 Hz 为预算起点，短时动态若需要更高采样，板端有界缓存后导出。

串口必须有单一所有者。现有 VOFA 要求独占设备，不能把 console、AsyncUart 和 VOFA 同时绑定诊断 UART。第一批按下面的代码变量选择互斥输出，文本与 JustFloat 不交织发送。

115200、8N1 理论上每秒约 11.52 kB。预算应计入帧头和文本长度；例如 16 个 float 的 JustFloat 帧连同 4 字节尾标是 68 字节，50 Hz 约 3.4 kB/s。诊断使用固定队列并记录丢帧数，主机断开不能阻塞控制。

诊断应回答“为什么没有动作”，例如遥控过期、尚未解锁、IMU 姿态过期、关节位置无效、对端 boot 不匹配、配置未确认。可显示全部未满足条件和首个直接阻塞原因，避免只给一个笼统 `ready=false`。

### 5.3 直接修改代码变量选择输出

在共享诊断配置头文件中集中放一个枚举变量，例如建议新建的 `include/robotics/vehicle/diagnostics_config.hpp`。以下仅为待实施的配置示意，不是本次新增的业务代码：

```cpp
enum class DiagnosticOutput { Log, Vofa };

// 只改这一处，然后重新编译、烧录需要运行的工程。
inline constexpr DiagnosticOutput diagnostic_output = DiagnosticOutput::Log;
```

看日志时设为 `DiagnosticOutput::Log`；看波形时将同一行改为 `DiagnosticOutput::Vofa`。所有独立上车工程和最终应用读取这一个配置值。它只选择诊断输出，不改变本工程启动哪些机构，也不改变解锁、控制周期、输入时效或故障恢复策略。

不增加角色宏、构建参数、额外 conf、串口命令、运行时模式状态机或 Flash 模式记忆。使用原有固定构建命令即可；修改变量后重新构建并烧录，已经烧录的固件不会自动改变。复位仍保持该二进制编入的模式，VOFA 固件不会复位后先输出一段日志。

| 配置值 | DAPLink 串口输出 | 电脑侧使用方式 |
| --- | --- | --- |
| `DiagnosticOutput::Log` | 启动身份、初始化错误、低频状态、故障事件等文本 | 串口终端，以共享配置中的波特率打开 COM 口 |
| `DiagnosticOutput::Vofa` | 纯 JustFloat 帧，包含测量值、有效位、状态/原因码 | VOFA 选择同一个 COM 口和波特率，协议选 JustFloat |

主机侧同一时刻只让一个程序占用 COM 口。切换时关闭当前工具，修改变量、重新编译烧录，然后用对应工具观察；无需修改现场接线，也无需发送任何命令。

VOFA 模式从启动起就不向诊断口输出 `LOG_*`、`printk`、shell 提示、启动 banner 等文本。普通故障通过波形中的状态/原因码和有效位报告，不自动退回日志模式。每个入口的 README 固定列出通道顺序、单位和布局版本；至少能看到目标、反馈、输出是否有效、阻塞原因和数据年龄。无效测量不能仅填零让人误认为实际零速；大序号/位掩码按现有遥测约定拆分，避免 float 精度丢失。

重新烧录或复位会丢失普通 RAM 中的故障记录。不要承诺改成日志固件后还能看到上一次 VOFA 运行的历史事件；需要追溯时先在电脑保存波形和状态码。第一版不为模式选择增加持久化故障缓存。

### 5.4 初始化与串口所有权

模式在启动时按配置确定一次，运行中不切换、不反复初始化 UART：

- 日志模式：启用诊断文本输出路径，不在同一 UART 上调用 `vofa_init()`。
- VOFA 模式：仅启动该口的 VOFA 输出路径，不启动其 console/shell 接收者，也不允许日志后台或其他路径向它直接写文本。
- 两种模式使用相同诊断设备和波特率；观测初始化不等待遥控、IMU、电机或对端就绪，初始化失败也有对应的文本错误或波形状态码。

目前 [vofa.h](../../include/lib/vofa/vofa.h) / [vofa.c](../../lib/vofa/vofa.c) 的 `vofa_init()` 会注册 UART 回调，并要求独占设备。固定模式下可沿用其单次初始化和有界 JustFloat 发送能力，不需要为本需求重构出运行时串口复用器，也不需要调用 `vofa_set_handler()` 接收切换命令。

日志选择仍需处理系统早期输出：仅在 `main()` 中判断变量并停止打印，不能保证更早初始化的日志后台、console 和启动 banner 已经停止。后续实现应让默认直写串口的日志/console 路径不自动占用该口，提供从初始化阶段就遵循该配置值的诊断日志后台；`printk/printf`、错误路径也要统一纳入输出策略。固定的公共系统配置可以为此调整一次，但日后用户只改上述变量，不能要求同时手改 Kconfig 才能得到纯 VOFA 数据。

这个诊断后台属于普通基础模块，不承担应用装配和执行循环。各独立入口自行初始化所需模块、提交自己的状态快照，仍遵守第 4 节的入口独立要求。故障时若系统已无法继续执行，波形可能停止；不要把停流误认为测量值维持不变，电脑侧应保留时间信息。

发送队列满时丢观测数据并计数，不能阻塞控制；电脑断开、VOFA 不读数据或切换电脑工具，都不能改变电机目标和运行授权。

### 5.5 第一批完成标准

- 所有上车入口和最终应用使用 DAPLink 实际连接的共享诊断口，不依赖目标板 USB。
- 只改代码中的 `diagnostic_output`，重新编译烧录即可选择日志或 VOFA；不需要串口命令、额外构建参数或同步修改其他配置。
- VOFA 模式从启动起没有文本混入，复位后保持 VOFA；日志模式能看到启动身份、初始化错误和当前阻塞原因。
- 遥控未连接、IMU/电机初始化失败、对端离线时，本板所选诊断输出仍能报告状态。
- 诊断断连和队列拥塞不阻塞控制；远端诊断尚未转发时明确其覆盖边界。

以上是后续实现与现场确认的标准，本次仅修改方案，未执行这些检查。

## 6. 独立上车阶段与覆盖缺口

下列入口名是建议目标，不表示仓库已有这些目录。已有 samples 用于迁移参考；不能仅凭目录名或历史编译通过记录认定可直接上车。不同板上的观察工程也分别有入口。

| 阶段 | 独立入口/职责 | 迁移参考 | 进入下一阶段前要得到的结论 |
| --- | --- | --- | --- |
| 0 诊断与板级资源 | `gimbal_io`、`chassis_io`；不启动执行器 | `hello`、`can_smoke`、当前日志 | 每次启动都有身份与资源表，现场能持续看到故障；控制台不占业务口 |
| 1 输入观察 | `gimbal_remote`、`gimbal_head_imu` | `communication/dr16`、`imu/dual_imu` | RC 通道/开关/超时正确；头部 IMU 字段新鲜，旋转轴、安装变换和参考清楚；不依赖 USB |
| 2 单轴机械闭环 | `gimbal_yaw_encoder`、`gimbal_pitch_encoder` | `gimbal_control`、电机速度/位置样例 | 单轴方向、零点、限位、速度内环和停机可解释；不要求另一轴、IMU、底盘在线 |
| 3 本地双轴 | `gimbal_joint_pair` | `command_gimbal` | 同一遥控与限位配置下双轴稳定；故障能定位到具体轴/总线 |
| 4 头部惯性 | `gimbal_inertial_yaw`、`gimbal_inertial_pair` | `inertial_gimbal` | 先 Yaw 保持，再双轴；IMU 断流可解释；暂不接大 Yaw 跟随 |
| 5 板间只观察 | `gimbal_link_observe`、`chassis_link_observe` | `communication/interboard` | 版本、方向、单位、年龄、boot、授权字段双方一致；打印解码但不启动电机执行器 |
| 6 大 Yaw 单独执行 | `gimbal_big_yaw_command`、`chassis_big_yaw` | `big_yaw`、`big_yaw_interboard` | 固定小范围请求下目标与实测单位一致，停止/超时有效；轮控未启动 |
| 7 双 Yaw 协同 | `gimbal_dual_yaw`，配第 6 阶段底盘入口 | `dual_yaw_centering` | 小 Yaw 偏差驱动大 Yaw 后减小，符号和反馈补偿一致；底盘平移仍不参与 |
| 8 底盘单模块 | 固定 FL/FR/RL/RR 的四个 `chassis_module_*` 工程 | `swerve` | 逐轮映射、舵向零点、轮驱方向和线速度量纲正确；不靠编译参数换轮 |
| 9 四舵轮与行走 | `chassis_four_modules`、`chassis_drive_link`，配独立发送入口 | `four_swerve` | 先本地解算与低速动作，再跨板行走；确认平移/自转方向、dt 和电流约束 |
| 10 单板组合/手动整车 | 独立的云台组合、底盘组合，再进入两个最终应用 | `gimbal_shared_can`、`vehicle_integration` | 共线 CAN 只有一个提交者，增加模块没有引入资源抢占、超时和周期退化 |
| 11 外部能力逐项接入 | 视觉观察、视觉执行、裁判观察、功率执行分别独立入口 | 视觉/裁判 sample、`chassis_power` | 观察先于控制；实测功率等必要输入已接入，失败能回到上一阶段 |
| 12 发射机构 | 摩擦空载、拨盘空载、空载组合、有载发射各独立入口 | `shooter_bench` | 真实热量/许可、归位参考和机构标定具备；空载成功不记为有载通过 |

第 2 阶段对 Pitch 的“单轴”是指仅该轴进入闭环，仍需考虑重力负载和机械支撑。第 8 阶段固定四个入口会有少量装配重复，可以接受；每个入口只选择共享配置中的固定模块，不能复制四份标定值。

所有阶段默认以实际 RC 操作授权或明确的台架操作输入开始，不能上电自动跑动作序列。若底盘现场没有遥控接收机，用已经通过的云台命令发送入口经板间提供输入；板间尚未验证时先做底盘无输出观察，不为绕过依赖伪造“永远有效”的授权。

每级保留最少的确认场景：正常小幅动作、撤销输入、该模块反馈断流、恢复后的当前命令行为；双板阶段再加单板重启和执行状态停更。实际停止延迟、稳态误差、峰值电流、周期峰值等阈值应在动作前按本机构约定并填写，不在文档里凭空宣布达标。本次只规划这些人工上车步骤，不执行测试或生成测试代码。

## 7. 额外能加快进度的补齐项

### 7.1 把“已实现”和“已上车通过”分开登记

保留一张小表即可，每模块记录：入口已具备、编译已完成、实板输入已确认、单机构已通过、组合已通过。历史方案中的“已实现”、确认 bool 和编译结果，不能自动升级成实板通过。

每次现场记录只填必要内容：

```text
日期/人员：
阶段与应用身份：
云台固件版本 / 底盘固件版本：
硬件配置版本 / 标定版本 / 协议版本：
本次唯一变化：
操作与预期（含量纲、允许误差、停止时限）：
观测到的目标 / 反馈 / 原因 / 时间：
结论：通过 / 失败 / 尚不能判断
日志或波形位置：
下一步与可回退固件：
```

一个异常只改变一个主要变量，优先分清输入、通信、控制、驱动、机械这几层。否则改 PID 的同时换 IMU、改方向、换遥控映射，即使恢复正常也难以复用结论。

### 7.2 保留能回退的阶段固件

保存每个通过阶段的二进制、实际配置、接线记录和操作说明，避免只保存 Git 提交但丢了当时使用的 overlay/conf。烧录前核对板角色和应用名，尤其两个同型号板卡。

日志和波形优先保存在电脑；不要为记录高频诊断直接持续写内部 Flash。以后确有断电保留需求，再单独设计小型故障记录。

### 7.3 先补会阻塞近期上车的缺口

近期处理：惯性 sample 的设备/驱动不一致、重复参数、串口所有权、独立单轴入口、原始反馈与门控原因可观测、对端协议和方向确认。

后续分别处理：实测功率输入及模型、真实发射热量/许可与拨盘参考、视觉参考会话及真实弹速/弹数反馈。它们不能靠开启功能开关补齐，也不应阻塞前面的机械云台和手动低速上车。

全局 `connections_confirmed` 等标志建议逐步细化为模块确认记录和对应配置值。单独调小 Yaw 时不应该因未标定的发射机构卡住；另一方面，小 Yaw 通过也不能一次性证明所有电机、IMU 和发射条件都通过。

### 7.4 清理文档入口，停止传播旧事实

后续以新的阶段目录 README 为现场操作说明；协议只有一个规范入口；历史方案保留日期和“历史记录”标签。优先修正文档与当前 IMU 后端、串口映射、确认标志、协议版本不一致的地方。

现有通用电机示例仍可保留给桌面学习，但应与“使用当前实车配置的上车工程”清楚区分。上车目录提供一张入口表，操作者不必翻几十个 sample 猜哪个适合当前接线。

| 第一批：先恢复可定位能力 | 双方协议最小契约、固定资源与配置基线、DAPLink 单串口日志/VOFA 代码变量选择、诊断/RC/IMU/单轴/板间观察入口 | 能说明“收到了什么、为什么不动、哪一轴反馈怎样”；只接 DAPLink 日志串口即可观察，改一个模式变量后重新编译烧录选择日志或 VOFA，无需目标板 USB；不依赖整车公共 `run()` |
| 第二批：打通机械主链 | 双轴、惯性、大 Yaw、双 Yaw、单舵轮和四舵轮独立工程 | 各级使用同一实车配置，逐级有记录，可退回刚通过的固件 |
| 第三批：再收敛整车 | 最终云台/底盘独立装配，共享配置；逐项补视觉、功率和发射 | 每项新增能力有明确输入、观测与失败行为，旧宏组合不再是现场构建入口 |

每批按“先完成该批配置整理和独立入口实现，再统一做最终编译，然后按上车表人工推进”的顺序执行。不要在拆一个函数、补一个宏之后就回到整车反复试烧；也不要为推进第一批先重构全部驱动、全部 sample。

下一次上车的第一个交付目标是：**同一套实车接线下，能分别运行无输出观察、小 Yaw 单轴、Pitch 单轴和头部 IMU 观察，并且每个入口都能在现场读到状态。** 这几项通过后，再恢复双轴和大小 Yaw 联动。
