# 云台遥控样例安全策略阅读指南

> 历史设计记录；旧 ready/Group 联锁/Session/恢复授权步骤不适用于当前实现。现行契约见[电机持续指令与独立自动恢复重构实施指南](电机持续指令与独立自动恢复重构实施指南.md)。

## 先看结论

本指南对应当前工作区的 `samples/robotics/gimbal_control/src/main.cpp` 与 `src/board_config.hpp`。这是“默认失能、满足条件后人工上锁、任何关键条件失效就撤销双轴输出”的样例。左拨杆上/下位用于确认安全状态，中位请求运行；右摇杆只在双轴已经运行时给角速度。`estop_latched` 表示“急停已锁存”，不是“此刻急停按钮正被按下”。

当前 `board_config.hpp` 中 `connections_configured = false`，`gimbalTask()` 在配置检查处提前退出。板级急停和复位函数（`board_config.hpp`）也都固定返回 `false`，尚未接入物理按钮。因此下面的急停分支是预留行为，当前配置下不会被触发。不要把这段软件逻辑理解为已经有物理断电急停。

## 一次控制循环怎样走

```text
遥控 UART -> RemoteReceiver 快照 -> 检查遥控新鲜度
                                     |
板级急停/复位请求 -> 急停锁存/清故障  |
两轴电机反馈 -> 稳定、位置参考和限位检查 |
控制循环耗时 -> dt 检查              |
                                     v
                     左拨杆上/下位取得 rearm_allowed
                                     |
                     左拨杆中位 + 其余条件都通过
                                     |
                      Group.enable() -> 双轴运行
                                     |
                      控制器更新 -> CAN commit
```

遥控接收由 `RemoteReceiver` 内部线程执行，每轮最多读取 8 块并休眠 1 ms；`main()` 启动模块，`gimbalTask()` 每约 5 ms 读取快照。UART 初始化失败会持续发布 InitFailed 和离线状态，控制线程的 fresh 因而为假。读取时会重新判断快照年龄，仍保留业务层 command_timeout_ms 检查。

### 三个容易混淆的变量

| 变量 | 含义 | 何时清零 |
| --- | --- | --- |
| `estop_latched` | 曾收到急停，须单独复位才能解除 | 急停已释放，且收到复位请求时 |
| `rearm_allowed` | 操作者已把左拨杆放到上/下位完成重新上锁动作 | 急停、复位、遥控/反馈/周期异常、拨杆未知、驱动掉出运行态、使能或控制失败时 |
| `enable_issued` | 本轮已经成功提交过 `Group.enable()` 请求；不表示双轴已真正运行 | 禁用、故障或使能失败时 |

`Group.enable()` 可能先进入 `enable_pending`，只有两轴就绪后才变为 `active`；见 `include/drivers/motor/group.hpp` 及 `drivers/motor/group.cpp`。只有 `gimbal.active()` 为真才更新轴控制器（`main.cpp`）。

### 实际使能条件

`gimbalTask()` 中的使能判断相当于：

```text
fresh = 遥控在线 && 最近有效帧距今 <= 100 ms
feedback_ok = yaw 与 pitch 的反馈都新鲜、位置有效、角度在允许范围内
timing_ok = 0 < 本轮间隔 <= 20 ms
new_command = 遥控帧的时间戳晚于两轴最近变为 ready 的时间

当 fresh、feedback_ok、timing_ok 都为真，未急停，
左拨杆在上/下位，两轴 ready，且 new_command 为真：rearm_allowed = true。

当 fresh、feedback_ok、timing_ok、new_command 都为真，
未急停，rearm_allowed 已为真，左拨杆在中位：requested = true。
```

`ready` 比“收到一帧反馈”更严格：电机驱动须处于禁用态、反馈稳定一段时间，限位轴还要有位置参考。两轴位置参考在 `Axis::ready()` 中检查并在需要时重建，见 `main.cpp`及 `drivers/motor/motor.cpp`。使能前还会重置两轴控制器，然后调用整个 `Group.enable()`（`main.cpp`）。同组任一轴不合格就不能正常运行两轴。

最短操作顺序：两轴和遥控先稳定 → 左拨杆放上或下位 → 收到在两轴 ready 之后的新遥控帧 → 左拨杆拨到中位 → 等待双轴使能完成。若左拨杆直接停在中位启动，`rearm_allowed` 初值为假，不会使能。

### 运行中怎么停、怎么恢复

`requested` 变假时，若组处于运行或等待使能，就调用 `Group.disable()`（`main.cpp`）。常见原因是左拨杆离开中位、遥控超时、反馈失效、控制循环超过 20 ms、急停锁存。控制器更新或 CAN 提交失败也会禁用全组并清除 `rearm_allowed`。驱动自行故障导致组退出运行时，也会清除 `rearm_allowed`。

普通“拨到上/下位”是可恢复的停机动作，不清除已经取得的 `rearm_allowed`；随后拨回中位，在其他条件仍满足时可以重新请求使能。故障、失联、超时、急停或控制错误清除 `rearm_allowed` 后，程序必须再次在健康状态下看到左拨杆处于上/下位，才可能重新使能。这里检查的是**拨杆位置**，没有检测“刚从中位拨过去”的边沿；如果故障恢复时拨杆已经停在上/下位，仍可重新取得许可。上/下位只是拨杆的安全位，不等于物理急停。

`Group.disable()` 撤销软件输出许可并向两个电机请求禁用，见 `drivers/motor/group.cpp`；安全报文由 CAN I/O 路径发送。它不是物理切断电机电源。pitch 轴失能时可能下坠，机构必须有支撑。右摇杆回中时控制器保留目标角度（配置中的 `hold_on_zero_rate = true`），不是禁用电机；角速度与目标角受 `lib/robotics/yaw_gimbal.cpp` 的速度/限位约束。

### `estop_latched` 的完整过程

1. 第一次读到 `emergencyStopRequested() == true`：立即请求禁用双轴，令 `estop_latched = true`，并清除使能请求和重新上锁许可（`main.cpp`）。
2. 急停输入恢复为 `false`，锁存仍为 `true`，因此 `requested` 仍为假；单纯松开急停不会重新使能。
3. 急停已释放，并读到一次 `takeEmergencyResetRequest() == true`：先禁用，再调用 `Group.clearFault()`，随后清除急停锁存、使能请求和重新上锁许可。故障清除失败会记录错误，但这里仍会清除 `estop_latched`；若电机故障未消除，`gimbal.ready()` 仍阻止使能。复位请求若发生在急停仍按下时，不执行复位，必须在释放后重新请求。
4. 复位后仍要等遥控与两轴健康，并重新把左拨杆置于上/下位，再拨到中位。

## 从遥测看卡在哪一步

`gimbalTask()` 每秒通过 VOFA 发送 11 个数。先看第 1 个 `fresh`，第 3 个 `rearm_allowed`，第 4 个 `estop_latched`，第 5/6 个 `active/enable_pending`。例如 `fresh=1, rearm_allowed=0, estop_latched=0, active=0` 时，先确认左拨杆是否经过上/下位，再检查反馈稳定、限位和控制周期。第 9 个数是组最近故障原因；第 10/11 个数是 CAN 最近错误码。通道完整顺序见样例 `README.md`。

## 阅读和实机自检

- 对照 `main.cpp`，在纸上按“启动、中位直启、上/下位后中位、遥控丢失、急停后释放、急停后复位”逐轮填写三个变量。这样最容易区分“锁存”和“当前输入”。
- 实机前先核对接线、零点、方向、机械限位与 pitch 支撑；`board_config.hpp` pitch 限位仍是占位值。完成核对前保持 `connections_configured = false`。
- 真要接入急停时，应先设计独立的物理安全回路，再按板级硬件实现两个预留函数，验证急停、释放、复位、再上锁各阶段的输出和遥测；本指南仅解释现有软件行为，不构成安全认证。
