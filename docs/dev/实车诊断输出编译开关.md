# 实车诊断输出编译开关

## 目标与现状

保留底盘和云台状态灯，用现有的 `CONFIG_SKYWALKER_VEHICLE_DIAGNOSTICS` 在编译时控制实车诊断输出。关闭时不编译 `vehicle_diagnostics.cpp`，因此不会创建其 VOFA 编码器、日志后端、输出队列、UART7 诊断 worker 或初始化函数。启用时保留现有 Log/VOFA 行为。

现有 `lib/robotics/CMakeLists.txt` 已按该 Kconfig 选择源文件；但所有实车入口仍调用 `Diagnostics`，关闭后现有声明没有定义，会链接失败。下面补充关闭时的空接口，并从两个正式应用中排除仅用于诊断的波形组装。`DiagnosticReason`、状态灯状态映射以及独立的 `CONFIG_SKYWALKER_STATUS_LED` 必须保留。

数据流：控制状态 → 状态灯映射 → 状态灯线程；另一路 → 诊断采样 → 诊断队列 → UART7。开关只切断第二路，不能改动控制状态产生或状态灯调用。

## 1. 提供关闭时的空接口

在 `include/robotics/vehicle/diagnostics.hpp` 中，保留 `DiagnosticReason`、`DiagnosticStatus` 和其上方所有定义；用以下条件编译替换现有整个 `Diagnostics` 类。启用分支的成员和声明必须与当前类一致：

```cpp
#if defined(CONFIG_SKYWALKER_VEHICLE_DIAGNOSTICS)
class Diagnostics {
public:
    int start(const char *application, const char *role, const char *limits = "see application profile");
    void event(const char *step, int result);
    void status(const DiagnosticStatus &);

private:
    const char *application_ = "boot";
    std::uint32_t sequence_ = 0;
    std::uint64_t next_sample_ms_ = 0, next_log_ms_ = 0, transition_ms_ = 0;
    DiagnosticReason last_reason_ = DiagnosticReason::Boot;
    int first_error_ = 0;
};
#else
class Diagnostics {
public:
    int start(const char *, const char *, const char * = "see application profile") { return 0; }
    void event(const char *, int) {}
    void status(const DiagnosticStatus &) {}
};
#endif
```

关闭时 `start` 返回 0、其他方法无操作，不访问设备、不启动线程；保留参数签名以兼容现有调用。`DiagnosticReason` 仍供状态灯使用，不能放在条件内。**空函数的实参仍会求值**：不要用条件编译包掉带业务副作用的调用，例如某些 bring-up 样例中的 `diagnostics.event("remote.start", remote.start())`，否则会跳过设备启动。

## 2. 去除正式应用的波形数据组装

在 `applications/sentry_chassis/src/main.cpp`，仅把 `const auto big_reason = ...` 开始到紧接其后的 `diagnostics.status({...});` 为止放进：

```cpp
#if defined(CONFIG_SKYWALKER_VEHICLE_DIAGNOSTICS)
// 原有 big_reason、unavailable、hd、trace 和 diagnostics.status 代码原样放在这里。
#endif
```

在 `applications/sentry_gimbal/src/main.cpp`，仅把紧接 `status_led.setStatus(...)` 后的 `const float unavailable = ...` 开始到紧接其后的 `diagnostics.status({...});` 为止放进同样的条件块。两处 `deadline += period` 必须留在条件块外。两板的 `reason`、`status_led.setStatus(...)`、电机提交、板间通信及控制循环全部留在条件块外。不要顺带移除可能用于控制或故障记录的变量和表达式。

这一步避免两个正式应用每周期构造 30 通道 `trace`；其他样例仍可使用空接口，调用实参可能仍会计算，但诊断输出实现不参与构建。已有 CMake 条件无需修改。

## 3. 选择开关

`config/vehicle/installed/base.conf` 当前包含 `CONFIG_SKYWALKER_VEHICLE_DIAGNOSTICS=y`，它被底盘、云台及上车样例共同使用。若要同时关闭这些入口的诊断输出，将这一行**替换**为：

```conf
CONFIG_SKYWALKER_VEHICLE_DIAGNOSTICS=n
```

要重新启用则替换回 `y`。这是编译期选择，必须重新构建并烧录相应板卡；只重烧云台不会改变底盘。不要改 `CONFIG_SKYWALKER_STATUS_LED=y`。本方案关闭的是实车 `Diagnostics` 后端，不保证移除 Zephyr 日志核心、所有其他独立日志后端、UART 驱动或其他应用自己的输出。当前共享配置禁用了 UART console 和标准 UART 日志后端；若其他构建配置另外启用它们，应单独检查。

## 4. 构建与上板

完成全部修改后，在仓库根目录由操作者运行一次所需应用的干净构建；若两板都需要该开关，分别构建：

```sh
west build -p always -b dm_mc02/stm32h723xx applications/sentry_chassis -d ../build/applications/sentry_chassis
west build -p always -b dm_mc02/stm32h723xx applications/sentry_gimbal -d ../build/applications/sentry_gimbal
```

确认无链接或 Kconfig 错误，再按既有流程烧录目标板。检查生成的 `.config` 中诊断开关状态与 `CONFIG_SKYWALKER_STATUS_LED=y`，并确认烧录的是新构建的目标。

在断开驱动或机械固定、人员远离运动部件的安全台架上按既有上电顺序启动，先不发送运动命令。关闭诊断时预计 UART7 无该后端的 VOFA/日志流，状态灯仍显示各状态；恢复开关并重建后应恢复原有诊断模式。若灯仍卡住，不能将问题归因于诊断输出，应继续检查灯线程和 SPI 波形。日志关闭会失去故障观测，不应依赖灯作为运动许可或故障保护。

## 完成清单

- [ ] 正式应用仅排除诊断采样，状态灯和控制循环不受条件编译影响。
- [ ] 依据目标板选择 `y` 或 `n`，无重复冲突配置，构建并烧录相应固件。
- [ ] 安全台架确认状态灯和诊断输出行为；记录硬件验证结果。
