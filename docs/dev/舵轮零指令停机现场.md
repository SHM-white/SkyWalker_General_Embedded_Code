# 舵轮零指令停机现场

日期：2026-10-05。此次重新读取 `/dev/ttyACM0`，由用户手动解锁、操作及归中复现。本文记录实际观测；本轮未修改业务源码、未编译、未刷写。此前获授权的 CAN 默认配置回退已完成，但此次实板对照仍出现故障。

## 1. 本轮结论

- 零运动指令也能触发 CAN2 Bus-off。用户明确反馈“归中也停了”，串口在 204534、214674、237693 ms 的 STOP 均记录目标速度和两路输出电流为零，两台电机实测转速也为零。
- 214521 ms 时已经解锁，遥控五通道归中，`coast=1`、`current=0.000/0.000`。当时 CAN2 TEC=0、REC=0；214669 ms 的普通目标帧 0x1fe 返回 -114，214674 ms 应用撤销授权。两个采样点相隔约 148 ms，不代表已经捕获这段时间内每次错误的发生时刻。
- 对应现场 CAN1 的 TEC 从 77 变成 150，也进入 Error Passive。另一次零指令故障时 CAN1 TEC=215。因此不能把问题局限为舵向 PID；两路通信均存在异常。
- 该现场不是目标速度越限、转向对齐门关闭、温度保护或控制周期越界导致的停机。零指令现场周期 5.1 ms，温度为 28°C/27°C。
- 恢复速度样例的 CAN 默认配置没有解决问题。用户观察到更容易停机；本轮没有严格配对测量两版故障率，不能给出变差倍数，也不能单凭该观察定位具体寄存器参数。
- 已定位直接触发链：CAN2 硬件 Bus-off → 发送回调 -ENETUNREACH（当前工具链 -114）→ 故障组撤销两路输出 → 遥控必须重新解锁。产生总线错误的最终根因仍未确定。

解读注意：

- STOP 中的 output 是上一轮成功的控制输出；`last_module_target` 则保留最近模块输入。这里故障发生在 transport/prerequisites 阶段，结合故障前整周期归中、Coast 日志及用户反馈判定零指令复现，不单独依赖一个 output 值。
- `feedback=reference` 出现在 CAN2 通信故障之后，不应倒过来认定为最初的舵角标定错误。
- `pre_restart_tx` 本次记录的是返回 -114 的普通目标帧，`purpose=0`。
- Bus-off 快照中的 TEC=0 不意味着故障前从未累积发送错误：Zephyr 驱动已经启动自动恢复，必须同时看 hw、回调错误、故障时间和重启前记录。
- bit0 统计不能直接当作“失败目标帧数量”。M_CAN 在 Bus-off 恢复期间也用 Bit0Error 状态报告所观察的恢复序列；CRC、form 等统计和故障前后状态应一起分析。参见 [Bosch M_CAN 手册 §2.3.14](https://www.bosch-semiconductors.com/media/ip_modules/pdf_2/m_can/mcan_users_manual_v331.pdf)。
- `healthy=1` 只代表样例所检查的反馈健康条件满足，不代表 CAN 错误率为零；`BusState::Running` 也不等同于硬件 Error Active。

## 4. 下一步应隔离的条件

用户已确认两台电机分别在速度控制样例中能稳定控制，保留这一事实作为对照；本轮不要求再次泛查接线，也不依据通信故障直接断言硬件损坏。

下一轮需要同一份零电流诊断固件比较以下三个独立启动场景，而非继续调整 PID 或随机更改采样点：

1. 仅启动 CAN2，与 GM6020 通信，持续发送零电流。
2. 仅启动 CAN1，与 C620/3508 通信，持续发送零电流。
3. 同时启动 CAN1/CAN2，分别持续发送零电流。

三场景使用相同板级时钟、1 Mbit/s、5 ms 发送周期、USB/遥控/日志配置及现有电机通信驱动，保持现有实物接线。每次从同样的启动状态开始，观察 60 秒或直到首次通信故障，记录硬件状态、TEC/REC、错误增量和首次故障快照。

诊断设计必须消除双电机故障组对“未启动一路”的依赖：不能直接注释掉一条 commit 后沿用现有 Group，这会引入命令超时并混淆结果。诊断只允许零电流，保留总线故障停发与人工重新开始的边界，不自动恢复运动。

若单路均正常而双路失败，才能确认同时运行是当前条件下的必要差异，再隔离发送重叠和共享资源；若单路也失败，则速度样例与诊断运行环境仍有其他差异需要对齐。目前没有实施此诊断固件，也没有把任何尚未验证的改动标作修复。
